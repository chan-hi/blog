## 증상

Private 서브넷에 있는 서버에서 외부로 나가는 통신이 **간헐적으로 실패**했다. 간헐적이라는 표현이 애매한데, 실제로 측정해 보면 패턴이 뚜렷했다.

| 항목 | 관측값 |
|------|--------|
| 성공한 요청의 응답 속도 | 약 0.16초 (정상) |
| 실패율 | 46~70% |
| 실패 형태 | 연결 자체가 수립되지 않음 (timeout) |
| 대상 | Google, Cloudflare, Naver, GitHub — **전 구간 동일** |

여기서 가장 중요한 단서는 **모든 외부 목적지에서 같은 패턴이 나온다**는 것이었다.

특정 목적지만 실패하면 그쪽 문제이거나 DNS 문제다. 그런데 서로 무관한 4개 서비스가 똑같이 절반씩 실패한다면, 목적지의 문제일 리가 없다. **경로상 어느 지점에 일관된 조건이 걸려 있다**는 뜻이다.

그리고 성공한 요청은 0.16초로 완전히 정상이었다. 느린 게 아니라 **되거나 안 되거나** 둘 중 하나였다. 이건 대역폭이나 부하 문제가 아니라는 신호다.

---

## 1차 검토에서 놓친 것

처음 확인 요청이 왔을 때 방화벽 규칙은 "이상 없음"으로 정리돼 있었다. NACL도 봤고 규칙에 문제가 없다는 판단이었다.

결론부터 말하면 **그 판단은 규칙의 문법만 본 것**이었다. 규칙이 문법적으로 올바른 것과, 그 규칙이 실제 트래픽 패턴을 통과시키는 것은 다른 문제다. 이 차이가 이번 장애의 핵심이었다.

## 계층별 배제

경로상의 조건을 찾아야 하니, 가능한 후보를 계층별로 하나씩 지웠다.

### 1단계 — ACG와 라우팅 배제

ACG(Access Control Group)는 **Stateful**이다. 나가는 요청을 허용하면 그에 대한 응답은 규칙과 무관하게 자동으로 허용된다. 즉 아웃바운드가 허용된 상태에서 응답만 선택적으로 막히는 일은 ACG에서는 일어나지 않는다.

라우팅도 마찬가지다. 라우팅이 잘못됐다면 100% 실패해야지 46~70%가 나올 수 없다.

두 후보를 지웠다.

### 2단계 — conntrack 세션 고갈 배제

연결 추적 테이블이 꽉 차면 신규 연결이 거부된다. 증상이 비슷해서 확인했다.

```bash
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
```

```
51
262144
```

262,144 중 51개. 고갈과는 거리가 멀다. 배제.

### 3단계 — 커널 드롭 배제

커널 레벨에서 패킷이 버려지고 있는지 확인했다.

```bash
netstat -s
```

의미 있는 드롭 카운터 증가가 없었다. 배제.

### 4단계 — DNS 배제

이름 해석 단계에서 실패한다면 IP로 직접 접속하면 성공해야 한다.

```bash
curl -v -o /dev/null https://<대상 IP>
```

IP 직접 접속도 **동일하게 절반가량 실패**했다. DNS는 원인이 아니다. 배제.

## 남은 구간

ACG·라우팅·세션 고갈·커널·DNS를 모두 지우고 나니 남은 것은 **NAT Gateway와 NACL 구간**이었다. 1차 검토에서 "이상 없음"으로 정리된 바로 그 구간이다.

여기서 두 가지를 따로 보지 않고 **함께 놓고** 봐야 했다.

### NACL은 Stateless다

이게 출발점이다. ACG와 달리 NACL은 상태를 추적하지 않는다. **나가는 트래픽과 들어오는 응답을 각각 별도의 규칙으로 허용해 줘야 한다.**

즉 아웃바운드가 허용돼 있어도, 그 요청에 대한 **응답이 들어오는 포트**가 Inbound 규칙에 없으면 응답이 버려진다. 요청은 나가는데 응답이 안 들어오니, 클라이언트 입장에서는 "연결이 수립되지 않음"으로 보인다. 증상과 정확히 일치했다.

### NAT Gateway의 SNAT 포트 배정 범위

NAT Gateway는 내부 서버의 요청을 자신의 공인 IP로 바꿔 내보내면서, 세션을 구분하기 위해 **출발지 포트를 임의로 재배정(SNAT)** 한다. 이때 사용하는 범위가 넓다.

| 항목 | 범위 |
|------|------|
| NAT Gateway가 배정하는 응답 포트 | **1024 – 65535** |
| NACL Inbound에 허용돼 있던 범위 | **32768 이상** |

여기서 답이 나왔다.

NAT Gateway가 **1024~32767 구간의 포트를 배정한 세션**은, 응답이 돌아올 때 NACL Inbound 허용 범위에 들어가지 않아 버려진다. 반면 32768 이상을 배정받은 세션은 정상 통과한다.

포트가 임의 배정되므로 **어떤 요청이 실패할지는 무작위**다. 그래서 "간헐적"으로 보였고, 두 구간의 크기 비율이 실패율 46~70%와 맞물렸다.

목적지와 무관한 이유도 설명된다. 이건 목적지가 아니라 **NAT Gateway가 포트를 어떻게 배정했는가**에 달린 문제였다.

## 조치

NACL Inbound에 **한 행만** 추가했다.

| 대상 | 방향 | 프로토콜 | 포트 범위 | 동작 |
|------|------|---------|----------|------|
| NAT Gateway 서브넷 | Inbound | TCP | **1024 – 32767** | Allow |

결과는 **100% 정상화**였다.

### 서버 서브넷은 건드리지 않았다

조치 범위를 최소화하는 게 중요했다. 서버 서브넷의 NACL은 기존 규칙이 이미 Linux ephemeral 포트 범위(`net.ipv4.ip_local_port_range`, 통상 32768–60999)를 포함하고 있었다. 서버가 직접 만드는 세션은 이 범위를 쓰므로 문제가 없다.

문제는 **NAT Gateway가 재배정한 포트**였고, 그건 NAT Gateway 서브넷의 문제였다. 그래서 그쪽만 고쳤다.

관련 없는 서브넷의 규칙까지 같이 열어두면 당장은 문제가 해결되지만, 나중에 왜 그 규칙이 있는지 아무도 설명하지 못하는 상태가 된다.

## 보안 영향 정리

규칙을 추가하는 조치라 보안 쪽 설명이 반드시 필요했다. 정리한 내용은 이렇다.

> 추가된 규칙은 **신규 인바운드 접속을 허용하는 것이 아니다.** NAT Gateway가 먼저 외부로 요청을 보낸 세션에 대한 **응답만** 통과시키는 구성이다. NACL이 Stateless이기 때문에 명시적으로 적어줘야 하는 것일 뿐, ACG가 Stateful하게 자동 처리하던 것과 동일한 범위다.
>
> 외부에서 이 포트로 새 연결을 시도하더라도, 그 앞단의 ACG와 NAT Gateway의 세션 테이블에 해당 세션이 없으면 도달하지 못한다.

## 정리

이 건에서 배운 것을 한 문장으로 줄이면 이렇다.

> **방화벽 규칙에 "이상 없음"은 문법이 맞다는 뜻이지, 실제 트래픽이 통과한다는 뜻이 아니다.**

Stateful(ACG)과 Stateless(NACL)를 같은 종류의 방화벽으로 취급하는 순간 이 장애는 보이지 않는다. 규칙 하나하나는 다 맞는데 조합이 틀린 경우이기 때문이다.

그리고 **"간헐적"이라는 표현을 그대로 받아들이지 않는 것**도 중요했다. 실패율을 측정하고, 성공한 요청의 응답 속도를 확인하고, 여러 목적지에서 같은 패턴이 나오는지를 보면 "간헐적"은 곧 "임의 배정되는 무언가가 조건을 가른다"로 좁혀진다. 그 지점부터는 후보가 몇 개 남지 않는다.

### 점검 순서 요약

| 순서 | 확인 대상 | 방법 | 배제 근거 |
|------|----------|------|----------|
| 1 | ACG / 라우팅 | 규칙 및 라우팅 테이블 | Stateful이라 응답 자동 허용, 라우팅 오류면 100% 실패 |
| 2 | 세션 고갈 | `nf_conntrack_count` / `_max` | 51 / 262144 |
| 3 | 커널 드롭 | `netstat -s` | 유의미한 카운터 증가 없음 |
| 4 | DNS | IP 직접 접속 | IP로도 동일 실패 |
| 5 | **NAT Gateway + NACL** | SNAT 포트 범위 ↔ NACL Inbound 범위 대조 | **원인** |
