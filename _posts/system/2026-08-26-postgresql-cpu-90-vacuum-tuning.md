## 이벤트

금융권 고객사의 Cloud DB(PostgreSQL)에서 **CPU 사용률이 90%까지 상승**하는 이벤트가 발생했다.

DB CPU가 높다는 건 증상이지 원인이 아니다. 이 상태에 도달하는 경로는 여러 개다.

| 후보 | 어떻게 CPU를 먹는가 |
|------|-------------------|
| 비효율 쿼리 | 인덱스를 못 타 풀스캔이 돈다 |
| 커넥션 급증 | 동시 실행 세션 수 자체가 많다 |
| 통계 정보 노후화 | 플래너가 잘못된 실행 계획을 고른다 |
| **테이블 비대화 (bloat)** | **죽은 튜플까지 훑느라 읽는 양이 늘어난다** |
| 배치/집계 작업 | 예정된 무거운 작업이 겹쳤다 |

먼저 할 일은 이 중 무엇인지 좁히는 것이었다.

---

## 1차 대응 — 원인 분석 보고서

지표를 수집해서 **원인 분석 문서를 직접 작성해 발신**했다. 스크린샷과 그래프를 16개 첨부했다.

보고서에 그래프를 여러 장 넣은 건 보기 좋으라고가 아니다. **시간축을 맞춰 놓고 겹쳐 봐야 상관관계가 보이기 때문**이다.

- CPU 그래프
- 커넥션 수 그래프
- 읽기/쓰기 I/O 그래프
- 특정 쿼리의 실행 빈도

CPU가 오르는 시점에 커넥션도 같이 올랐는지, 아니면 커넥션은 평소와 같은데 CPU만 올랐는지에 따라 원인 후보가 갈린다. 커넥션이 그대로인데 CPU만 오르면 **요청 수가 아니라 요청 하나당 비용이 커졌다**는 뜻이고, 그러면 쿼리 계획이나 테이블 상태 쪽을 봐야 한다.

### 보고서를 쓰는 것 자체가 대응의 일부다

고객사 입장에서 필요한 건 "조치했습니다"가 아니라 **"왜 그랬고, 다음에 또 그러면 어떻게 되는가"** 다. 특히 금융권은 내부 보고 라인이 있어서, 담당자가 위에 설명할 수 있는 형태의 문서가 필요하다.

그래서 지표 캡처를 근거로 붙이고, 확인된 사실과 추정을 구분해서 적었다. 확인되지 않은 것을 단정하면 나중에 그 문장 때문에 신뢰를 잃는다.

## 재발 — Vacuum 튜닝

이후 같은 증상이 다시 나타났고, 이때 **Vacuum 튜닝**으로 대응했다.

### PostgreSQL에서 죽은 튜플이 CPU를 먹는 구조

PostgreSQL은 MVCC를 쓴다. `UPDATE`나 `DELETE`를 해도 기존 행이 즉시 사라지지 않고, **더 이상 보이지 않는 죽은 튜플(dead tuple)** 로 남는다. 다른 트랜잭션이 아직 그 버전을 볼 수도 있기 때문이다.

이 죽은 튜플을 정리하는 게 `VACUUM`이고, 보통 `autovacuum`이 자동으로 돈다.

문제는 **정리 속도가 쌓이는 속도를 못 따라갈 때** 생긴다.

1. 갱신이 잦은 테이블에 죽은 튜플이 쌓인다
2. 테이블 물리 크기가 커진다 (bloat)
3. 같은 결과를 얻는 데 **더 많은 페이지를 읽어야 한다**
4. I/O와 CPU 사용량이 함께 오른다
5. 부하가 높아지니 autovacuum은 더 밀린다

5번이 고약하다. **부하가 높을수록 정리가 밀리고, 정리가 밀릴수록 부하가 높아지는 되먹임**이 생긴다. 그래서 어느 순간 갑자기 CPU가 튀는 것처럼 보인다.

### 손봐야 하는 지점

기본 autovacuum 설정은 범용값이라, 갱신이 매우 잦은 테이블에서는 잘 안 맞는다. 확인하고 조정할 대상은 대략 이렇다.

| 항목 | 무엇을 결정하는가 |
|------|-----------------|
| `autovacuum_vacuum_scale_factor` | 테이블 크기 대비 몇 %가 죽은 튜플이 되면 vacuum을 돌릴지 |
| `autovacuum_vacuum_threshold` | 최소 몇 건부터 대상으로 볼지 |
| `autovacuum_vacuum_cost_limit` | 한 번에 얼마나 일하고 쉴지 (I/O 영향 조절) |
| `autovacuum_max_workers` | 동시에 몇 개 테이블을 정리할지 |

특히 `scale_factor`는 **비율**이라 큰 테이블일수록 임계치가 커진다. 1억 건짜리 테이블에서 기본값 0.2면 2천만 건이 죽은 뒤에야 vacuum이 시작된다. 그때는 이미 늦다. 이런 테이블은 **테이블 단위로 별도 설정**을 주는 게 맞다.

```sql
ALTER TABLE 대상테이블 SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_threshold = 1000
);
```

전역 설정을 건드리면 모든 테이블에 영향이 가고, 조용하던 테이블까지 vacuum이 자주 돌면서 오히려 I/O가 늘 수 있다. **문제가 있는 테이블만 좁혀서 조정하는 게 안전하다.**

### 확인용 쿼리

죽은 튜플이 얼마나 쌓였는지, 마지막 vacuum이 언제였는지는 이걸로 본다.

```sql
SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum,
       last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

`n_dead_tup`이 `n_live_tup`에 근접하거나 넘어가는 테이블, 그리고 `last_autovacuum`이 오래된 테이블이 후보다.

## 남은 것

기록을 정확히 남기기 위해 밝혀 두면, **이 건의 최종 원인 확정과 재발 방지 성공 여부까지 검증된 상태는 아니다.** 지표상 CPU 상승과 대응, 그리고 Vacuum 튜닝 적용까지가 확인된 범위다. "조치했더니 해결됐다"를 결론으로 쓰려면 이후 관측 기간이 더 필요하다.

이런 구분을 남겨 두는 이유는, 나중에 이 기록을 다시 볼 때 **무엇이 확인된 사실이고 무엇이 추정이었는지** 가 섞이면 판단이 오염되기 때문이다.

## 정리

**1. "DB CPU 높음"은 증상이다.** 쿼리, 커넥션, 통계, bloat, 배치 중 무엇인지부터 좁힌다.

**2. 그래프는 시간축을 맞춰 겹쳐 본다.** CPU만 오르는지 커넥션도 같이 오르는지가 후보를 절반으로 줄인다.

**3. PostgreSQL은 죽은 튜플이 CPU를 먹는다.** 그리고 부하와 vacuum 지연은 서로를 악화시킨다.

**4. autovacuum 기본값은 큰 테이블에 안 맞는다.** `scale_factor`가 비율이라 커질수록 임계치가 멀어진다.

**5. 전역이 아니라 테이블 단위로 조정한다.** 문제 없는 테이블까지 건드리면 다른 문제가 생긴다.

**6. 보고서에서 확인된 사실과 추정을 구분한다.** 단정한 문장 하나가 나중에 신뢰를 깎는다.
