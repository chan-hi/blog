## 배경

유통 고객사의 점포 확장 일정에 맞춰 **서버를 1대에서 50대로 늘려야** 하는 작업이 있었다.

기존 절차는 콘솔 수작업이었다.

1. 콘솔에서 서버를 하나 만든다
2. 만들어진 서버를 로드밸런서 대상 그룹에 등록한다
3. 50번 반복한다

측정해 보니 **10대에 약 20분**이 걸렸다. 50대면 단순 환산으로 100분이다.

---

## 자동화하기 전에 절차를 먼저 뜯어봤다

"오래 걸리니 자동화하자"로 바로 가면 잘못된 것을 자동화하게 된다. 그래서 단계별로 무엇을 하고 있는지부터 분해했다.

| 단계 | 사람이 판단하는가 | 실수가 발생하는가 |
|------|-----------------|-----------------|
| 서버 생성 (사양·이미지·서브넷 선택) | 첫 1대에서만. 나머지는 동일 형태 반복 | 낮음 (콘솔이 검증) |
| **LB 대상 그룹 등록** | 없음 | **높음** |

두 가지가 보였다.

**첫째, 사람이 판단할 구간이 사실상 없었다.** 50대가 전부 같은 사양, 같은 이미지, 같은 서브넷이었다. 첫 1대의 사양을 정하고 나면 나머지 49대는 그것의 복제였다. 판단이 없는 반복은 자동화 대상으로 딱 맞다.

**둘째, 진짜 위험한 지점은 생성이 아니라 등록이었다.** 서버 생성은 실패하면 콘솔에 바로 보인다. 그런데 로드밸런서 대상 그룹 등록 누락은 **조용히 실패한다.** 서버는 멀쩡히 떠 있고, 대상 그룹에만 안 들어가 있다. 트래픽이 그 서버로 안 갈 뿐이다.

50대 중 1대를 빠뜨렸다고 해서 서비스가 죽지 않는다. 나머지 49대가 받아준다. **그래서 발견이 늦다.** 부하가 몰리는 시점에야 "왜 용량이 계획보다 부족하지"로 드러난다.

---

## 그래서 등록까지 같은 실행에 묶었다

여기가 이 작업의 핵심 판단이었다.

서버 생성만 Terraform으로 옮기고 대상 등록을 콘솔에 남겨두는 방법도 있었다. 그게 더 쉽고, 시간 단축 효과도 대부분 얻는다.

하지만 **등록을 손에 남기는 한 누락 가능성은 그대로다.** 오히려 생성이 빨라져서 50대가 한 번에 쏟아지면, 손으로 등록해야 할 대상이 한꺼번에 50개가 되어 누락 확률이 올라간다. 자동화가 문제를 키우는 경우다.

그래서 **서버 생성과 로드밸런서 대상 등록을 하나의 Terraform 실행으로 통합**했다. 리소스 간 의존 관계를 코드에 명시해 두면 서버가 만들어진 뒤 대상 등록이 이어지고, 둘 중 하나만 된 상태가 남지 않는다.

```hcl
# 구조만 옮긴 예시
resource "ncloud_server" "app" {
  count = var.server_count
  # 사양·이미지·서브넷은 변수로
}

resource "ncloud_lb_target_group_attachment" "app" {
  count            = var.server_count
  target_group_no  = var.target_group_no
  target_no        = ncloud_server.app[count.index].instance_no
}
```

핵심은 문법이 아니라 **`count` 하나로 대수를 바꾸고, 등록이 생성에 의존하도록 걸어둔 구조**다.

## 결과

| 항목 | 이전 | 이후 |
|------|------|------|
| 소요 시간 | 10대당 약 20분 (50대 환산 약 100분) | **50대 일괄 20분 이내** |
| 증설 시간의 대수 의존성 | 대수에 비례해 증가 | **비례하지 않음** |
| 대상 그룹 등록 누락 | 사람이 놓칠 수 있음 | 구조적으로 발생하지 않음 |

시간 단축은 약 80%다. 다만 이 수치는 **소요 시간이 본인 기준 진술값(미계측)** 이고, 100분은 10대 실측을 대수 비례로 환산한 값이라는 점을 밝혀둔다.

그리고 개인적으로는 시간보다 **두 번째 줄이 더 중요하다고 본다.** 100분이 20분이 된 것은 이번 한 번의 이득이지만, "대수가 늘어도 시간이 늘지 않는다"는 것은 다음 확장부터 계속 남는 이득이다. 100대가 되어도 절차가 그대로다.

## 정리

자동화를 검토할 때 스스로 묻게 된 질문 두 개를 남겨둔다.

**1. 이 절차에서 사람이 실제로 판단하는 구간이 어디인가?**
판단이 있는 곳은 남기고, 없는 곳만 옮긴다. 전부 옮기려다 보면 예외 처리가 늘어나 코드가 콘솔보다 복잡해진다.

**2. 조용히 실패하는 지점이 어디인가?**
큰 소리로 실패하는 작업(서버 생성)은 사람이 해도 금방 알아챈다. 진짜로 자동화해야 하는 건 **실패해도 티가 안 나는 작업**이다. 이번 경우엔 로드밸런서 대상 등록이 그랬고, 그래서 시간 단축보다 그쪽을 먼저 봤다.
