## 순서가 반대인 환경이 있다

일반적인 구축은 이렇게 흘러간다. 요구사항을 받고, 아키텍처를 그리고, 동작하게 만들고, 마지막에 보안을 붙인다.

금융존과 공공 사업은 이 순서가 반대다. **보안 요건이 먼저 문서로 존재하고, 아키텍처가 거기 맞춰 그려진다.** "이렇게 하면 더 편한데요"가 통하지 않고, 요건을 충족하지 못하면 구성 자체가 반려된다.

이 글은 금융권과 공공 모빌리티 두 환경에서 3-Tier를 구성하며 정리한 기준이다.

---

## 1. 계층 배치 — 무엇을 Public에 둘 것인가

3-Tier의 출발점은 Web / WAS / DB를 어디에 둘지다.

| 계층 | 배치 | 이유 |
|------|------|------|
| Web | Public 서브넷 (LB 경유) | 외부 트래픽의 진입점 |
| **WAS** | **Private 서브넷** | 외부에서 직접 도달할 이유가 없다 |
| **DB** | **Private 서브넷** | 마찬가지 |

당연해 보이지만 실제 환경에서는 자주 지켜지지 않는다. 개발 편의를 위해 WAS에 공인 IP를 붙여 두고 그대로 운영에 넘어가는 경우가 흔하다.

Private에 두면 배포와 디버깅이 불편해진다. 그 불편을 감수하는 대신 **접근 경로를 따로 만든다**는 게 다음 항목이다.

---

## 2. 관리자 접근은 SSL VPN으로 한정

Private 서브넷의 서버에 어떻게 접근할 것인가. 흔한 방법은 Bastion 서버를 Public에 두는 것이다. 동작은 한다.

공공 요건 환경에서는 **SSL VPN으로 한정**했다.

차이는 인증 지점이다. Bastion은 그 자체가 인터넷에 노출된 서버라, 결국 "인터넷에 열려 있는 SSH 포트"가 하나 남는다. 아무리 키 인증을 걸어도 노출 자체는 사라지지 않는다. SSL VPN은 **네트워크에 들어오는 단계에서 인증**하므로 서버 포트가 인터넷에 보이지 않는다.

운영 관점에서 부수 효과도 있다. VPN 계정을 회수하면 접근이 한 번에 끊긴다. Bastion 방식은 서버마다 키가 흩어져 있어 퇴사자 처리 같은 상황에서 누락이 생긴다.

---

## 3. ACG는 최소 권한으로 — 상위에서 하위로만

ACG(Access Control Group)를 설정할 때 기준을 하나로 잡았다.

> **상위 계층에서 하위 계층으로 가는 방향만 허용한다.**

| 방향 | 허용 |
|------|------|
| LB → Web | O |
| Web → WAS | O |
| WAS → DB | O |
| Web → DB | **X** |
| DB → WAS | **X** |

`Web → DB`를 막는 게 핵심이다. 웹 서버가 DB에 직접 붙을 일은 정상 동작에서는 없다. 이 경로가 열려 있으면, 웹 서버가 뚫렸을 때 공격자가 WAS를 거치지 않고 바로 DB에 도달한다.

**출발지를 IP 대역이 아니라 ACG로 지정**하는 것도 중요하다. 대역으로 열면 그 대역 안에 나중에 추가되는 서버까지 자동으로 권한을 얻는다. ACG로 지정하면 그 그룹에 속한 서버만 통과한다.

그리고 트래픽이 **반드시 LB를 경유해야만 서버에 도달**하도록 구성했다. 서버 IP로 직접 오는 요청은 받지 않는다. 이렇게 해야 WAF 같은 앞단 장비를 우회하는 경로가 생기지 않는다.

---

## 4. ACG와 NACL을 계층별로 나눠 쓴다

두 가지를 같은 종류로 취급하면 안 된다. 성격이 다르다.

| | ACG | NACL |
|---|---|---|
| 적용 단위 | 서버(인터페이스) | 서브넷 |
| 상태 추적 | **Stateful** | **Stateless** |
| 응답 트래픽 | 자동 허용 | **명시적으로 허용해야 함** |
| 규칙 | Allow만 | Allow / Deny |

역할을 이렇게 나눴다.

- **NACL** — 서브넷 경계에서 굵직하게 거른다. 이 서브넷에 애초에 들어올 수 없는 트래픽을 차단.
- **ACG** — 서버 단위로 세밀하게 통제한다. 어느 그룹이 어느 그룹에 접근할 수 있는지.

NACL이 Stateless라는 점은 실무에서 반드시 사고로 이어진다. 아웃바운드를 허용해 놓고 그에 대한 **응답 포트를 Inbound에 안 열어 두면 통신이 실패**하는데, 규칙 자체는 문법적으로 멀쩡해 보인다. 이 주제로 실제 장애를 겪은 적이 있어 [별도 글](/blog/posts/nat-gateway-nacl-ephemeral-port-mismatch/)로 정리해 뒀다.

## 5. 보안 상품 조합 — 무엇이 무엇을 막는가

금융존 구축에서는 보안 상품을 계층별로 배치했다. 이름이 비슷해서 혼동되기 쉬운데, 막는 대상이 각각 다르다.

| 상품 | 막는 것 | 위치 |
|------|--------|------|
| **AntiDDoS** | 대량 트래픽으로 서비스를 마비시키는 공격 | 최외곽 |
| **WAF** | HTTP 요청 내용의 공격 (SQLi, XSS 등) | 웹 앞단 |
| **IDS / IPS** | 네트워크 레벨의 침입 시도 탐지·차단 | 네트워크 경로 |
| **AntiVirus** | 서버 내부의 악성 파일 | 서버 |

핵심은 **하나가 다른 하나를 대체하지 않는다**는 것이다. WAF가 있으니 IPS는 없어도 된다는 식의 판단이 가끔 나오는데, WAF는 HTTP 계층을 보고 IPS는 그 아래를 본다. 대량 트래픽은 둘 다 못 막고 AntiDDoS가 필요하다.

---

## 6. 서브계정 분리

인프라만큼 중요한 게 콘솔 권한이다.

운영을 하다 보면 계정이 정리되지 않은 상태를 자주 만난다. 여러 사람이 마스터 계정을 공유하고, 누가 무엇을 바꿨는지 추적이 안 되는 상태다. 장애가 났을 때 "누가 이 설정을 언제 바꿨나"에 답할 수 없다.

금융존 구축에서 서브계정 체계를 정리한 기준은 두 가지였다.

1. **사람 단위로 계정을 나눈다.** 공유 계정이 있으면 감사 추적이 성립하지 않는다.
2. **역할에 필요한 권한만 준다.** 운영자에게 결제·계정 관리 권한을 주지 않는다.

---

## 정리

보안 요건이 먼저 정해진 환경에서 일하며 정리된 것들이다.

**1. 요건 문서를 먼저 읽고 아키텍처를 그린다.** 그리고 나서 요건에 맞추면 대부분 다시 그리게 된다.

**2. Private에 두는 불편은 접근 경로 설계로 해결한다.** 불편하다고 Public으로 올리지 않는다.

**3. ACG는 방향과 출발지 그룹으로 통제한다.** IP 대역으로 열면 나중에 들어오는 서버가 권한을 상속받는다.

**4. LB 우회 경로를 남기지 않는다.** 앞단 보안 장비가 있어도 서버 IP 직접 접근이 열려 있으면 의미가 없다.

**5. ACG와 NACL을 같은 것으로 취급하지 않는다.** Stateful과 Stateless의 차이가 실제 장애로 나타난다.

**6. 보안 상품은 계층별로 다른 것을 막는다.** 하나로 대체되지 않는다.

**7. 인프라를 잠갔으면 콘솔 권한도 잠근다.** 마스터 계정 공유는 앞의 모든 조치를 무력화한다.
